## Verified guest saved-search management

- `POST /api/saved-searches/access-links` accepts only `{ email }`, normalizes it, and returns a generic HTTP202 receipt. The response does not disclose search existence or delivery success. SMTP and trusted `FRONTEND_URL` must be configured before a link can be sent.
- The single-use management link lasts30minutes, stores only a SHA-256 digest, and uses `/dashboard#saved-search-token=...`. The browser clears the fragment before mounting the application. An explicit confirmation POST, not a GET/email-scanner visit, consumes the token.
- `POST /api/saved-searches/access-links/consume` accepts only `{ token }` and returns `{ success, data: { token, email, expiresAt } }`. This is a separate opaque30-day management session, not an admin JWT. Its digest is stored; expiry/revocation are enforced even before TTL cleanup. Frontend storage is sessionStorage only.
- `X-Saved-Search-Session` is required for private list/detail/update/delete/matching results. `GET /api/saved-searches?page=1&limit=20` returns a scoped `data` array and `pagination` (`currentPage`, `totalPages`, `totalSearches`, `hasNextPage`, `hasPrevPage`); limit is at most100. The legacy `/user/:email` route cannot change the verified scope. Foreign IDs return404.
- `DELETE /api/saved-searches/session` revokes that exact management session. An admin JWT alone never grants guest management access. Tokens/digests are not returned in search DTOs.
- Public `POST /api/saved-searches` may record a pending intent and request a link, but returns only the generic202 receipt and leaves alerts inactive. Consuming a link does not activate any pending/legacy subscription. The verified owner must explicitly opt an individual search in; only then are `verifiedAt`/`alertConsentAt` stamped. Email/recipient is immutable. Invalid nested settings and unknown fields are rejected.
- DTOs expose consent dates as date-or-null and invalid legacy criteria as null, never an unfiltered `{}` replay. Public browse/criteria replay remains public, while private saved-result endpoints require proof.
- All saved-search responses, including JSON parser errors, carry no-store. Rate limits are bounded, process-local IP/email controls; validate shared/upstream protection for the actual multi-instance topology before deployment.

## Alert execution and uncertainty

The former send-capable GET `/api/saved-searches/admin/check-matches` is disabled. Sending requires an explicit persisted-owner POST or the once-run worker, valid configuration, and the alert feature opt-in. The CLI defaults to dry-run. A timer is an operator responsibility, not silently installed/activated by this checkpoint.

Approved cadence is immediate per invocation, daily 09:00 and weekly Monday 09:00 Africa/Nairobi. Durable leases and per-search/property delivery records prevent overlapping/repeated sends. Execution awaits the unique delivery/lease indexes before claims; distinct sent, unknown and sending batches conservatively consume quota/cadence because they may have delivered. Only active, verified, explicitly consented searches and currently available matches qualify. Matching uses bounded cursor batches while retaining legacy/effective-price semantics; exact result counts still scan candidates, so bounded memory is not proof of unlimited throughput.

SMTP has no transactional exact-once guarantee. A transport attempt with an ambiguous outcome or a stale sending claim is quarantined as `unknown` rather than automatically resent. Preserve the ledger and investigate provider evidence before any explicitly approved recovery; do not delete delivery records or reset counters to force a retry. Delivery states are `queued`, `sending`, `sent`, `failed`, `unknown`; only definite `notification_not_configured` failures can retry, at most three attempts with bounded backoff. A claimed/ambiguous send is not evidence of provider acceptance.
